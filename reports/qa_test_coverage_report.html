Observaciones del Código — Hallazgos Preventivos

6 items
OBS-001 | XSS Potencial en Frontend: La tabla de órdenes usa template literals con innerHTML y concatenación directa de datos del API (${order.notes}, ${order.status}). Si la API retorna datos con HTML/JS malicioso (ej. en notes), el frontend lo renderiza sin sanitizar. El backend almacena lo que recibe sin filtrar. Severidad: Crítica.
OBS-002 | Conexiones DB sin Connection Pool: Cada request abre y cierra una conexión nueva con psycopg2.connect(). Bajo carga concurrente, esto puede agotar conexiones del servidor PostgreSQL. Recomendación: implementar psycopg2.pool.ThreadedConnectionPool o migrar a SQLAlchemy con pooling.
OBS-003 | Status "cancelled" solo en backend: El API valida cancelled como status válido en POST, pero el frontend (select en formulario y modal) solo ofrece pending, processing, completed. No hay forma de crear o editar a "cancelled" desde la UI. Inconsistencia funcional.
OBS-004 | Mismatch de payload para POST /api/orders: La prueba de creación de órdenes `tests/apis/test_api_orders.py::test_02_post_order_persists_in_db` y el flujo de prueba `test_03_get_orders_shows_inserted_data` usan un factory de datos (`fixture/order_factory.py`) que construye campos UnitPrice y Status en lugar de unit_price y status. Esto no coincide con el contrato del backend y puede causar fallos de validación en el POST.
OBS-005 | Edit modal no precarga datos actuales: Al hacer clic en "Edit", el modal abre con quantity="" y status="pending" por defecto, sin cargar los valores actuales de la orden. El usuario pierde contexto de qué está editando y puede sobrescribir con valores incorrectos sin darse cuenta.
OBS-006 | Password hardcodeado en código fuente: El DB_PASSWORD tiene un fallback hardcodeado 'M1l02025' en el código. Si se pushea a un repo público, expone credenciales. Recomendación: usar solo os.getenv() sin fallback, o usar un secrets manager.
